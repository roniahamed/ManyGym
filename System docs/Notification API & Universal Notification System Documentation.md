# Universal Notification System & FCM API Integration Documentation

This document defines the architectural specification, data contracts, and client integration guidelines for the **Universal Notification System** and **Firebase Cloud Messaging (FCM) Real-Time Push Delivery** in ManyGym.

---

## 1. Architectural Overview & System Design

ManyGym features a dual-channel notification pipeline designed to balance persistent in-app engagement with high-throughput real-time mobile push delivery.

```text
                  ┌──────────────────────────────────────────────┐
                  │            Event Trigger In Domain           │
                  │ (Reaction, Comment, Join Request, Staff, Msg)│
                  └───────────────────────┬──────────────────────┘
                                          │
                 ┌────────────────────────┴────────────────────────┐
                 ▼                                                 ▼
    [Standard Domain Events]                           [Chat / Encrypted Messages]
  (Reaction, Comment, Request, Invite)                 (E2EE Chat Messages)
                 │                                                 │
                 ▼                                                 ▼
   1. Persist `Notification` in DB                     1. Store in `EncryptedMessage` only
   2. Broadcast via Django Channels                    2. Broadcast via Conversation Room WS
   3. Enqueue Celery FCM Push Task                     3. Enqueue Celery FCM Push Task
                 │                                                 │
                 └────────────────────────┬────────────────────────┘
                                          ▼
                      ┌───────────────────────────────────────┐
                      │    Celery Worker (Async Task)         │
                      │  Fetch Active Client Device Tokens    │
                      └───────────────────┬───────────────────┘
                                          ▼
                      ┌───────────────────────────────────────┐
                      │    integrations.fcm.FCMClient         │
                      │  Dispatches Multicast FCM Push Alert  │
                      └───────────────────┬───────────────────┘
                                          ▼
                      ┌───────────────────────────────────────┐
                      │ Client Devices (Android / iOS / Web)  │
                      └───────────────────────────────────────┘
```

### 1.1 Dual-Channel Operating Rules

1. **Universal In-App Notifications (`Notification` Table)**:
   - Used for **Reactions**, **Comments & Replies**, **Member Joining Requests**, **Gym Staff Invitations**, **Social Follows**, and **System Alerts**.
   - Persisted to the PostgreSQL `notifications` table.
   - Increment user unread count badge.
   - Broadcast live across Django Channels WebSocket personal user channel (`chat_user_{user_id}`).
   - Dispatched to active mobile/web client devices via FCM push.
   - **Self-Notification Suppression**: Users NEVER receive notifications generated by their own actions (e.g. liking their own post or commenting on their own thread).

2. **Real-Time Message Notifications (FCM Push Only)**:
   - Used for **End-to-End Encrypted (E2EE) Messages**.
   - **DOES NOT** persist a generic row in the `notifications` table. E2EE messages already have authoritative storage in the chat database (`EncryptedMessage`) and their own conversation unread counters.
   - Immediately dispatches a high-priority FCM push notification and WebSocket room notification to recipient devices so incoming chats alert users in real time.

## 2. General Configuration & Headers

* **Base URL:** `/api/v1/notifications/`
* **Authentication:** JWT Bearer Token (`Authorization: Bearer <token>`)
* **Accepted Content Types:** `application/json`
* **Standard Request Headers:**
  * `Authorization: Bearer <token>` — Required for all notification and device token endpoints.
  * `X-Gym-Context: <gym_uuid>` — Optional header when managing notifications in gym workspace context.

## 3. Endpoints Specification

### 3.1 List In-App Notifications
* **Method:** `GET`
* **Path:** `/api/v1/notifications/`
* **Summary:** List User Notifications
* **Description:** Retrieves a paginated list of persistent in-app notifications for the authenticated user, ordered with newest first. Supports filtering by read state and event type.
* **Authentication:** Required (JWT Bearer)
* **Query Parameters:**
  * `is_read` (boolean, optional): Filter by `true` (read) or `false` (unread).
  * `notification_type` or `type` (string, optional): Filter by event type (`reaction`, `comment`, `comment_reply`, `member_request`, `member_request_accepted`, `member_request_rejected`, `gym_invite`, `follow`, `system`).
  * `page` (integer, optional, default: 1): Page number.
  * `page_size` (integer, optional, default: 20, max: 100): Page size.

#### Response: `200 OK`

### 3.2 Get Unread Notification Count
* **Method:** `GET`
* **Path:** `/api/v1/notifications/unread-count/`
* **Summary:** Get Unread Notification Count
* **Description:** Returns the total count of unread persistent notifications for badge calculation in the client mobile or web UI.
* **Authentication:** Required (JWT Bearer)

#### Response: `200 OK`
```json
{
  "unread_count": 5
}
```

### 3.3 Mark Single Notification as Read
* **Method:** `PATCH` (or `POST`)
* **Path:** `/api/v1/notifications/{notification_id}/read/`
* **Summary:** Mark Notification as Read
* **Description:** Marks an individual notification as read and sets the `read_at` timestamp.
* **Authentication:** Required (JWT Bearer)
* **Path Parameters:**
  * `notification_id` (UUID, required): The UUID of the target notification.

#### Response: `200 OK`

### 3.5 Delete Notification
* **Method:** `DELETE`
* **Path:** `/api/v1/notifications/{notification_id}/`
* **Summary:** Delete Notification
* **Description:** Permanently removes a notification from the user's history.
* **Authentication:** Required (JWT Bearer)

#### Response: `204 No Content`

### 3.6 Register Client Device Token
* **Method:** `POST`
* **Path:** `/api/v1/notifications/devices/`
* **Summary:** Register Device Token
* **Description:** Registers or updates an FCM push notification device token for the authenticated user. Automatically reactivates re-registered tokens and enforces a maximum active device threshold per account.
* **Authentication:** Required (JWT Bearer)
* **Request Body:**
```json
{
  "token": "fK19_eXampleFcmTokenFromFirebaseClientSDK_1234567890",
  "device_id": "a823e-902b-4211",
  "device_name": "iPhone 15 Pro",
  "platform": "ios"
}
```
* **Validation Rules:**
  * `token`: Required string (max 500 characters).
  * `platform`: Optional enum (`android`, `ios`, `web`), defaults to `android`.
  * `device_id`: Optional string (max 120 characters).
  * `device_name`: Optional string (max 150 characters).

#### Response: `201 Created`
```json
{
  "id": "11223344-5566-7788-9900-aabbccddeeff",
  "device_id": "a823e-902b-4211",
  "device_name": "iPhone 15 Pro",
  "platform": "ios",
  "is_active": true,
  "last_seen_at": "2026-11-17T19:40:00Z",
  "created_at": "2026-11-17T19:40:00Z"
}
```

---

### 3.7 Unregister Device Token
* **Method:** `POST` (or `DELETE`)
* **Path:** `/api/v1/notifications/devices/unregister/`
* **Summary:** Unregister Device Token
* **Description:** Deactivates an active device token upon user sign-out to prevent push delivery to shared or decommissioned hardware.
* **Authentication:** Required (JWT Bearer)
* **Request Body:**
```json
{
  "token": "fK19_eXampleFcmTokenFromFirebaseClientSDK_1234567890"
}
```

#### Response: `200 OK`
```json
{
  "unregistered": true,
  "message": "Device token unregistered successfully."
}
```

## 4. FCM Push Payload Format

When notifications are dispatched to mobile or web clients, FCM receives both standard notification alerts and high-priority data payloads:

```json
{
  "notification": {
    "title": "Alex Morgan reacted to your post",
    "body": "Alex Morgan reacted 🔥 to your post."
  },
  "data": {
    "notification_type": "reaction",
    "target_type": "post",
    "target_id": "402e3b8a-91d8-4f51-b842-fa328b9a1024",
    "action_url": "/posts/402e3b8a-91d8-4f51-b842-fa328b9a1024",
    "reaction_code": "fire",
    "reaction_emoji": "🔥"
  },
  "android": {
    "priority": "high",
    "notification": {
      "sound": "default",
      "channel_id": "manygym_notifications"
    }
  },
  "apns": {
    "payload": {
      "aps": {
        "sound": "default",
        "badge": 1
      }
    }
  }
}
```

### 4.1 Message FCM Push Payload Format
For real-time E2EE messaging push alerts:
```json
{
  "notification": {
    "title": "John Doe",
    "body": "Sent you an encrypted message."
  },
  "data": {
    "type": "chat_message",
    "conversation_id": "dcf72dc1-0b47-43ef-81de-11fc3d17180d",
    "message_id": "5f3a2b1c-9e8d-4a7b-b6c5-1a2b3c4d5e6f",
    "sender_type": "user",
    "sent_at": "2026-11-17T19:42:00Z"
  }
}
```

## 5. WebSockets Real-Time Event Dispatch

In addition to push delivery via FCM, all active in-app notifications are broadcast in real time across Django Channels:

* **Personal Channel Group:** `chat_user_{user_id}`
* **Gym Channel Group:** `chat_gym_{gym_id}`
* **Event Type:** `incoming_notification`

### Event Payload:
```json
{
  "type": "incoming_notification",
  "id": "8c3f4e2b-1a98-4c32-b7e1-8930412850a1",
  "notification_type": "reaction",
  "title": "Alex Morgan reacted to your post",
  "body": "Alex Morgan reacted 🔥 to your post.",
  "target_type": "post",
  "target_id": "402e3b8a-91d8-4f51-b842-fa328b9a1024",

  "data": { ... },
  "is_read": false,

}
```

## 6. Error Responses Reference

| Status Code | Code | Reason |
| :--- | :--- | :--- |
| `400 Bad Request` | `VALIDATION_ERROR` | Empty or malformed device token string. |
| `401 Unauthorized` | `UNAUTHORIZED_CONTEXT` | Missing or invalid JWT authorization header. |
| `404 Not Found` | `not_found` | Notification not found or belonging to another user. |
| `403 Forbidden` | `permission_denied` | Attempting to access another user's notification. |
