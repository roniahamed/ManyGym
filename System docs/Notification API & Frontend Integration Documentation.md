# Notification & Device Token API Frontend Integration Documentation

This document defines the complete architectural design, data contracts, and client integration guidelines for the **Universal Notification System** and **Firebase Cloud Messaging (FCM) Push Delivery** in ManyGym.

---

## 1. Architectural Overview & System Flow

ManyGym features a dual-channel notification pipeline designed to balance persistent in-app engagement with high-throughput real-time mobile and web push delivery.

```text
                  ┌──────────────────────────────────────────────┐
                  │            Event Trigger In Domain           │
                  │ (Reaction, Comment, Join Request, Staff, Msg)│
                  └───────────────────────┬──────────────────────┘
                                          │
                 ┌────────────────────────┴────────────────────────┐
                 ▼                                                 ▼
    [Standard Domain Events]                           [Chat / Encrypted Messages]
  (Reaction, Comment, Request, Invite)                 (E2EE Chat Messages)
                 │                                                 │
                 ▼                                                 ▼
   1. Persist `Notification` in DB                     1. Store in `EncryptedMessage` only
   2. Broadcast via Django Channels                    2. Broadcast via Conversation Room WS
   3. Enqueue Celery FCM Push Task                     3. Enqueue Celery FCM Push Task
                 │                                                 │
                 └────────────────────────┬────────────────────────┘
                                          ▼
                      ┌───────────────────────────────────────┐
                      │    Celery Worker (Async Task)         │
                      │  Fetch Active Client Device Tokens    │
                      └───────────────────┬───────────────────┘
                                          ▼
                      ┌───────────────────────────────────────┐
                      │    integrations.fcm.FCMClient         │
                      │  Dispatches Multicast FCM Push Alert  │
                      └───────────────────┬───────────────────┘
                                          ▼
                      ┌───────────────────────────────────────┐
                      │ Client Devices (Android / iOS / Web)  │
                      └───────────────────────────────────────┘
```

### 1.1 Dual-Channel Operating Rules

1. **Universal In-App Notifications (`Notification` Table)**:
   - Used for **Reactions**, **Comments & Replies**, **Member Joining Requests**, **Gym Staff Invitations**, **Social Follows**, and **System Alerts**.
   - Persisted to the PostgreSQL `notifications` table.
   - Increments unread badge count.
   - Broadcast live across Django Channels WebSocket personal user channel (`chat_user_{user_id}`).
   - Dispatched to active mobile/web client devices via FCM push.
   - **Self-Notification Suppression**: Users NEVER receive notifications generated by their own actions (e.g. reacting to own post or commenting on own thread).

2. **Real-Time Message Notifications (FCM Push Only)**:
   - Used for **End-to-End Encrypted (E2EE) Messages**.
   - **DOES NOT** persist a generic row in the `notifications` table. E2EE messages already have authoritative storage in the chat database (`EncryptedMessage`) and their own conversation unread counters.
   - Immediately dispatches a high-priority FCM push notification and WebSocket room notification to recipient devices so incoming chats alert users in real time.

## 2. General Configuration & Headers

* **Base URL:** `/api/v1/notifications/`
* **Authentication:** JWT Bearer Token (`Authorization: Bearer <access_token>`)
* **Content-Type:** `application/json`
* **Standard Headers:**
  * `Authorization: Bearer <access_token>` (Required for all endpoints)
  * `Content-Type: application/json` (Required for endpoints with request body)
  * `X-Gym-Context: <gym_uuid>` (Optional; switches notification context to gym workspace. Permitted in `CORS_ALLOW_HEADERS`. Alternatively, a gym-context JWT token from `/api/v1/auth/switch-context/` automatically resolves gym context without requiring this header)

## 3. Global Error Envelope & HTTP Status Codes

### 3.1 Standard Error Format

All error responses return the following JSON structure:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Invalid input provided.",
  "details": {
    "token": [
      "This field may not be blank."
    ]
  }
}
```

### 3.2 Error Fields Specification

| Field | Type | Nullable | Description |
| :--- | :--- | :--- | :--- |
| `code` | string | No | Machine-readable error code (`VALIDATION_ERROR`, `UNAUTHORIZED_CONTEXT`, `PERMISSION_DENIED`, `RESOURCE_NOT_FOUND`, `METHOD_NOT_ALLOWED`) |
| `message` | string | No | Human-readable summary of the error |
| `details` | object \| array \| null | Yes | Field-level validation errors or additional context; `null` if none |

### 3.3 HTTP Status Codes

| Status Code | Error Code | Scenario |
| :--- | :--- | :--- |
| `200 OK` | — | Successful retrieval, update, or action confirmation |
| `201 Created` | — | Resource created (e.g., device token registration) |
| `204 No Content` | — | Resource deleted successfully (empty body) |
| `400 Bad Request` | `VALIDATION_ERROR` | Malformed JSON, missing required fields, invalid UUIDs, invalid enum choices, or array limits exceeded |
| `401 Unauthorized` | `UNAUTHORIZED_CONTEXT` | Missing, invalid, or expired JWT Bearer token |
| `403 Forbidden` | `PERMISSION_DENIED` | Attempting to access or mutate a notification belonging to another user |
| `404 Not Found` | `RESOURCE_NOT_FOUND` | Notification or device token does not exist |
| `405 Method Not Allowed` | `METHOD_NOT_ALLOWED` | Unsupported HTTP method on the route |

## 6. FCM Push Notification Payloads

When push notifications are received by client apps via Firebase Cloud Messaging, FCM delivers the following standard payloads:

* **Stringified Data Guarantee:** All values inside the `data` dictionary (e.g. `target_id`, `actor_id`, `action_url`, `conversation_id`, `message_id`, `sender_id`) are guaranteed to be serialized as string primitives.
* **Web Push Delivery:** Tokens registered with `platform: "web"` receive FCM push dispatches configured via `WebpushConfig` (carrying `WebpushNotification` with `title`, `body`, and `data`), ensuring full compatibility with Web Push Service Workers.

### 6.1 Standard In-App Notification Push Payload

Delivered to mobile and web clients via FCM for all standard in-app notifications:

```json
{
  "notification": {
    "title": "New Comment",
    "body": "Jane Doe commented on your post: 'Great workout session!'"
  },
  "data": {
    "notification_type": "comment",
    "target_type": "post",
```

## 7. WebSocket Realtime Events (Django Channels)

Clients connected to the user WebSocket channel receive real-time events over the following room:

* **Channel Room:** `chat_user_{user_id}` or `chat_gym_{gym_id}`
* **Event Type:** `notification.alert`
